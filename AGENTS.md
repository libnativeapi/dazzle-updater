# dazzle updater workspace

A cross-platform software update framework. dazzle updater is its own design: it does not
replicate Sparkle's or WinSparkle's API or configuration conventions (no
`SUFeedURL`-style keys). Sparkle compatibility is confined to an optional `AppcastSource`
module that reads Sparkle appcasts and converts them into dazzle updater releases (feed-level
compatibility only); the [release index](specs/release-index.md) is dazzle updater's own format.
The workspace holds the C++ core library, its language bindings and the design specs
together. `core/` and `bindings/*` are plain
directories; each can be split into its own repository later
(`git subtree split --prefix=core`) without changing the layout.

## Layout

```
core/               # the C++ core library (layers described in core/AGENTS.md)
bindings/           # language bindings: rust/, dart/, csharp/, go/
examples/           # complete apps on a UI framework: <framework>_<module>_example
prototype/          # Storybook prototypes of UpdaterUI (specs/updater-ui.md); pnpm, standalone
specs/              # design rules for core/
tools/codegen/      # the code generator, run through ./codegen
Makefile            # make build | examples | rust | dart | csharp | go | flutter | mygo | codegen | check | test | clean
```

## Code generation

The C++ headers in `core/src/` are the source of truth. `./codegen` generates from them
the C ABI (`core/src/capi/<module>_c.*`, `core/include/dazzle_updater.h`) and each binding's
declarations and wrapper classes. See [tools/codegen/README.md](tools/codegen/README.md).

- After changing a public header, run `./codegen` and commit the regenerated files with
  the header change. `./codegen check` fails when they are out of date.
- Never edit a file that starts with `// AUTO-GENERATED by tools/codegen. DO NOT EDIT.`
- A new module's header goes into `API_HEADERS` in `tools/codegen/main.py`.
- Watch the output for `warning: skipped ...`: a method with an unsupported type is left
  out of every binding.

## Architecture

- `core` — the source of truth for the public API. Interface layer `core/src/*.h`,
  per-platform implementations under `core/src/platform/<os>/` (macOS, Windows, Linux,
  Android, iOS, OHOS), C ABI under `core/src/capi/`, single public include
  `core/include/dazzle_updater.h`.
- `bindings/*` — each binding wraps the C ABI from `core/` and builds `core/` from source
  with CMake: Rust links the static library; Dart (as a native asset), C# (next to the
  assembly) and Go (cgo, built with `go generate`) use the shared library
  (`-DDAZZLE_BUILD_SHARED=ON`). See bindings/README.md.

## Design specs

Start at [specs/README.md](specs/README.md) before adding or reshaping public API in
`core/src/`.

## Conventions

- Verify a core change with `make test`: it checks the generated files are current, then
  builds and runs the core examples and the Rust, Dart, C# and Go tests. The framework apps
  in `examples/` need their SDK and are built separately (`make flutter`, `make mygo`).
- Linux has its own example and its own end-to-end test: `make demo-linux` starts a local
  signed feed and runs `core/examples/updater_ui_example` around an application directory
  (a Linux application *is* a directory), and `ctest -R dazzle_updater_linux_install_e2e` covers the
  download, the signature check, the replacement and the restart. `core/tools/updater_ui_preview`
  renders every window state to a PNG without a desktop session (see its README for the
  Xvfb line), which is the quickest way to look at the GTK 4 windows.
- Do not add Co-Authored-By trailers to commits.
